# Design: add an architecture overview

Issue: #69 (Task). Branch and change key: `69-architecture-overview`.

## Intent

The repo has grown past what its folder names explain. One page, written for people first, lets the owner follow how a request moves through the app without reading the code, and keeps agents building new areas the same way. Agents read the same page.

## Goals

Issue #69's "Done when" list:

- [ ] `docs/explanation/architecture.md` covers the six parts, with the three flows as diagrams
- [ ] It's linked from the docs index, the explanation index and `AGENTS.md`
- [ ] `AGENTS.md` says to update it when the structure changes

## Non-goals

- No code changes.
- No ADR: the page describes decisions already recorded (0009, 0016–0019). The PR summary says so.
- No tooling to render or check Mermaid. GitHub renders it.

## Anti-goals

- Copying what the code or the ADRs already say, which would go stale. The page links to files and ADRs instead.
- Describing anything that isn't on `main` now (the "new area" section is a pattern, clearly marked as the way to add one, not as existing code).

## Approaches

1. **One explanation page, plus index links and one `AGENTS.md` line** (chosen, approved by the owner on 2026-11-19). It's what the issue asks for, and it follows Diátaxis ([ADR 0002](../../docs/explanation/decisions/0002-structure-docs-with-diataxis.md)).
2. Split into several pages (concepts, auth, flows). Rejected: the issue wants a one-page map, and the content fits on one page.
3. Put the map in `AGENTS.md` or `README.md`. Rejected: it's written for people first, and explanation belongs under `docs/explanation/`.

## The page: `docs/explanation/architecture.md`

The same voice as the other docs: short, plain sentences, the 💡 explanation framing, and a "Where next" footer. Relative links to code files (`../../src/...`) and ADRs (`decisions/...`).

1. **Where code runs.** A table: `src/proxy.ts`, `route.ts`, a `"use server"` file, `page.tsx`/`layout.tsx` (Server Components by default), a `"use client"` file, each with where it runs, when, and the example in this repo. Also `import "server-only"`, which makes the build fail if browser code imports the file. Then a short mapping to familiar backend terms: proxy ≈ middleware or guard, route handler and Server Action ≈ controller, `AuthService` ≈ service interface with two providers, `createAuthService` ≈ factory. Facts checked against the installed Next.js 16 docs: Proxy replaced Middleware in v16 and runs on Node.js by default; a file-level `"use server"` exposes every export as a Server Function, which is a public endpoint.
2. **The folder map.** One line each: `src/proxy.ts`, `src/app/` (routes, one folder per address), `src/components/` (shared UI; `ui/` is generated by shadcn), `src/lib/` (logic with no UI; `auth/`, `messages/`, small helpers). Plus `__tests__/` next to the code, `e2e/` and `supabase/` outside `src/`. (The owner agreed to add `messages/` and `__tests__/`.)
3. **The auth module (`src/lib/auth/`).** The `AuthService` and `CookieJar` ports in `types.ts`, the Supabase and mock adapters, `createAuthService` choosing by `APP_ENV` through `pickAuthBackend`, the two jars (the proxy's request/response jar and `authServiceForRequest` in `next-cookie-jar.ts`), and which files are server-only.
4. **The three flows**, as Mermaid sequence diagrams:
   - Opening a page: browser → proxy → `hasSession()` → redirect to `/login` or `/`, or render the page; `Cache-Control: private, no-store`; `BfcacheReload` reloads a page restored from the back/forward cache.
   - Logging in: form → field check in the browser → `logIn` Server Action → checks again → `signIn` → cookie set → browser goes to `/`; or an error code → popup.
   - Logging out: button → `POST /logout` (cross-site check) → `signOut` → 204 → browser goes to `/login`; a redirect means already logged out; a failure shows a popup.
5. **Adding a new area.** The pattern for business data, for example `src/lib/matches/`: a port in `types.ts`, a Supabase adapter, a factory, server-only, and the session check next to the data that ADR 0018 requires (asking Supabase directly, not only trusting the gate's local check). Screens in `src/app/<area>/`, tests in `__tests__/`.
6. **Environments.** A table of `APP_ENV` values (`local`, `preview`, `test`, `production`, missing) against where each is used (laptop, Vercel preview, CI, Vercel production), and the backend each picks. Links to ADRs 0016–0019, without repeating them.
